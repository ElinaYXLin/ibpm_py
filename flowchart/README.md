# flowchart/

Two diagrams of the `py/` (Python port) codebase, plus the scripts and raw
data used to build them, so you can regenerate or check every edge later.

## What's here

```
flowchart/
  generate_module_graph.py        auto-generated import graph (script)
  generate_execution_flowchart.py hand-traced "what calls what" (script)
  execution_flow_refs.csv         file:line citation for every box/edge in the hand-traced diagram
  output/
    module_dependency_graph.png       auto-generated
    module_dependency_edges.csv       raw edge list behind that PNG
    main_execution_flowchart.png      hand-traced
```

### 1. `module_dependency_graph.png` -- mechanical, whole-package import graph

Generated by parsing every file in `py/*.py` with Python's `ast` module and
recording every `from .x import y` / `from . import x` statement as an edge
`x.py -> y.py` ("x imports y"). No judgment calls: it's a 1:1 rendering of
`module_dependency_edges.csv`. Node color is a purely cosmetic role grouping
(entry point / solvers / model / core data / geometry+motion / io+utils) and
does not affect which edges are drawn. Vertical position ("layer") is computed
automatically as the longest import-dependency chain from that module, so the
entry point (`ibpm.py`) floats to the top and leaf modules (`grid.py`,
`bc.py`, `tangent_se2.py`, ...) sink to the bottom.

This diagram answers "which files does X.py depend on / get depended on by,"
not "in what order do things execute" -- e.g. `ib_solver.py` imports
`cholesky_solver.py` at module load time, which says nothing about *when*
during a run a `CholeskySolver` actually gets constructed or called.

### 2. `main_execution_flowchart.png` -- hand-traced runtime call sequence

A strict left-to-right layered call graph. **Column 0 is every statement of
interest in `py/ibpm.py`'s `main()`, top to bottom, in execution order** --
so "where does `ibpm.py` call into X" is always answered by scanning
straight down column 0 (e.g. `IBSolver` is reached from the
`solver.advance(x)` box, `ibpm.py:452`, near the bottom of that column).
Call depth increases left to right: column 1 is what a column-0 statement
calls directly, column 2 is what column-1 code calls, and so on, out to
column 5 (the innermost breakdown of `ProjectionSolver.solve()`). Two
column-0 statements have real call depth worth expanding --
"build model + solver" (`ibpm.py:318-347`, fans out into
`IBSolver.__init__`/`createAllSolvers`/`createSolver`) and
`solver.advance(x)` (`ibpm.py:452`, fans out into the full substep detail:
nonlinear term, projection solve, Helmholtz/Poisson solves, state refresh);
everything else in column 0 is a flat one-line call, so it has no rightward
branch. This is a judgment call about which calls are "interesting" (it
does not show every function call, e.g. it collapses `print(...)` progress
messages and asserts).

**Every arrow is labeled with the `file:line` of the call site it leaves
from** (i.e. the line in the *upstream* box's own code where the downstream
box gets called -- not the line the downstream function is defined on).
Box text itself is deliberately short (just the call/expression); look at
the arrow feeding into a box to find out exactly where it's invoked. The
same citations are also listed in `execution_flow_refs.csv` in execution
order.

## How to check these against the code

You do not have to trust either diagram -- both are designed to be checked
mechanically:

**For `module_dependency_graph.png`:**
1. Open `output/module_dependency_edges.csv`.
2. Pick any row, e.g. `ib_solver,navier_stokes_model`.
3. Run `grep -n "^from \.navier_stokes_model import" py/ib_solver.py` (or just
   open `py/ib_solver.py` and look at its import block) and confirm the
   import is really there.
4. To regenerate the whole thing from scratch (e.g. after editing `py/`):
   `python3 flowchart/generate_module_graph.py`. If you add/remove/rename an
   import, the picture and the CSV change together -- there's no hand-edited
   state to go stale.

**For `main_execution_flowchart.png`:**
1. Open `execution_flow_refs.csv`. Each row is one box or one arrow in the
   diagram: a `step` (matches the numbered stage in the picture), a short
   description, the call itself, and a `file:line`.
2. Open that `file` at that `line` in your editor and confirm the call shown
   really happens there. For example, row `"Call ProjectionSolver"` cites
   `py/ib_solver.py:209` -- open that file and you'll find
   `self._solver[i].solve(a, b, x.omega, x.f)` on that line.
3. For the "polymorphic" `N(x)` box (5 different overrides depending on
   `-model` flag), each subclass's line is cited separately -- check
   `NonlinearIBSolver.N`, `LinearizedIBSolver.N`, etc. in `py/ib_solver.py`.
4. Line numbers will drift as the code changes. If a citation looks wrong,
   `git log -p -L<line>,<line>:<file>` shows how that line has moved/changed
   over time, or just re-open the current file -- the surrounding function
   name in the box text should still be there even if the exact line shifted
   by a few rows.
5. The diagram is not auto-regenerated from the code (unlike the module
   graph) -- it's asserted by me and worth spot-checking, especially the
   control-flow bits (loop-back arrows, which branch is taken for which
   `-model` value) rather than just individual calls.

## Regenerating

```
cd ibpm_py
python3 flowchart/generate_module_graph.py
python3 flowchart/generate_execution_flowchart.py
```

Requires `matplotlib` (already a transitive dependency via `py/`'s numpy/scipy
stack; install with `pip install matplotlib` if needed). No other
dependencies (deliberately avoided `networkx` / `graphviz` so this runs
anywhere Python + matplotlib does).
